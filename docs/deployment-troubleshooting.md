# ERPNext/Dokploy Deployment Troubleshooting Record

## Purpose and current state

This record documents the deployment path used to make
`*.erpsite.devlouix.com`, `erpsite.devlouix.com`, the ERPNext platform, and
verified custom domains work in one Dokploy Traefik installation.

HTTPS is currently served by:

- automatic exact-host HTTP-01 certificates for custom domains;
- a manually managed wildcard certificate for ERPNext tenant sites;
- Dokploy's existing Docker and file providers.

The manual wildcard setup is deliberate. It avoids the failing LEGO Spaceship
DNS provider while retaining Spaceship for DNS management.

## Final architecture

```text
Internet
  |
  +-- port 80/443 --> Dokploy Traefik
                         |
                         +-- Docker provider --> platform-api, frappe-frontend
                         +-- file provider --> Dokploy dynamic configuration
                         |                    + ERPNext custom-domain routes
                         |                    + manual wildcard certificate
                         |
                         +-- /etc/dokploy/traefik/certs --> installed acme.sh files

acme.sh container
  |
  +-- Spaceship DNS API --> _acme-challenge TXT records
  +-- DNS-01 --> apex + wildcard certificate
  +-- /acme.sh --> certificate account state
  +-- /certs --> shared certificate files for Traefik
```

## Components and current responsibilities

| Component | Responsibility |
|---|---|
| `traefik-public` | HTTPS termination, Docker discovery, file-provider routes |
| `platform-api` | Platform UI/API router |
| `platform-worker` | Generates exact-host Traefik YAML routes |
| `frappe-frontend` | Wildcard tenant and ERPNext site upstream |
| `acme-sh` | Issues and renews the ERPNext wildcard certificate |
| `/etc/dokploy/traefik/dynamic` | Shared Dokploy/ERPNext dynamic configuration |
| `/etc/dokploy/traefik/certs` | Certificate files read by Traefik |

## Issue history

### 1. Custom-domain routes shared the wrong storage

**Symptom:** The worker and Traefik used separate named-volume storage
locations, so ERPNext could not reliably distribute route files into Dokploy's
watched directory.

**Resolution:** Keep the worker route directory configurable, but mount
Dokploy's existing dynamic directory into the worker:

```text
/etc/dokploy/traefik/dynamic
  -> /var/lib/erpnext/custom-domain-routes in platform-worker
```

Traefik mounts that host directory read-only at the same container path. Route
generation only uses files named `custom-domain-<sha256>.yml`.

**Future constraint:** Do not give the worker ownership of an unrelated
topology. Changes here require an explicit directory-layout review.

### 2. Traefik linked routers to multiple services

**Symptom:**

```text
Router erpnext-api cannot be linked automatically with multiple Services
Router erpnext-sites cannot be linked automatically with multiple Services
```

The Compose labels inherited both Dokploy-generated services and ERPNext
services.

**Resolution:** Explicitly bind each ERPNext router to its service:

```yaml
- "traefik.http.routers.erpnext-api.service=erpnext-api"
- "traefik.http.routers.erpnext-sites.service=erpnext-sites"
```

Do not create overlapping Dokploy Domain entries for the same Compose router.

### 3. Spaceship DNS-01 failed inside LEGO

**Symptom:** LEGO/Traefik failed while adding the Spaceship TXT record:

```text
spaceship: The request is invalid.
domain: The length of domain must meet the minimum required length.
```

The provider could read Spaceship DNS records but could not produce the needed
zone API request in the deployed Traefik/Lego combination.

**Resolution:** Do not keep retrying the same Spaceship/LEGO configuration.
Use `acme.sh` for wildcard issuance outside Traefik while retaining Spaceship
as the DNS provider. Keep exact custom domains on Traefik HTTP-01.

### 4. Custom domains should not depend on DNS-01

**Symptom:** The custom-domain default resolver was changed from `letsencrypt`
to Spaceship and therefore tried to use DNS-01.

**Resolution:** Custom-domain routes use the ordinary exact-host HTTP-01
resolver:

```dotenv
CUSTOM_DOMAIN_CERT_RESOLVER=letsencrypt
```

Each custom hostname needs:

- a public A/AAAA record pointing to the VPS;
- public port 80;
- an exact-host route generated by the worker.

Wildcard DNS-01 remains independent from this flow.

### 5. `acme.sh` combined issue and install incorrectly

**Symptom:**

```text
The domain 'erpsite.devlouix.com' is not a cert name.
Cannot find path: '/acme.sh/erpsite.devlouix.com'
```

The certificate was not yet issued, and the separate install operation looked
for incomplete state.

**Resolution:** Issue and install are separate operations.

```bash
docker exec acme-sh acme.sh --issue \
  --dns dns_spaceship \
  -d erpsite.devlouix.com \
  -d '*.erpsite.devlouix.com' \
  --dnssleep 30 \
  --keylength ec-256

docker exec acme-sh acme.sh --install-cert \
  -d erpsite.devlouix.com \
  --ecc \
  --cert-file /certs/erpsite.crt \
  --key-file /certs/erpsite.key \
  --fullchain-file /certs/erpsite.fullchain.crt
```

Always use the `acme.sh` executable explicitly in `docker exec`.

### 6. ECC storage uses an `_ecc` directory

**Symptom:** Certificate state appeared under:

```text
/acme.sh/erpsite.devlouix.com_ecc
```

The original lookup omitted `--ecc`, and the RSA-only directory name was not
present.

**Resolution:** With `--keylength ec-256`, all certificate operations use
the ECC directory and include `--ecc`.

```bash
docker exec acme-sh find /acme.sh -maxdepth 1 -type d -name '*erpsite*'
docker exec acme-sh acme.sh ls -la /acme.sh/erpsite.devlouix.com_ecc/
```

### 7. ZeroSSL required account setup

**Symptom:** Issuance stopped before DNS validation with:

```text
No EAB credentials found for ZeroSSL
Please update your account with an email address first.
```

`acme.sh` defaults to ZeroSSL in the deployed version.

**Resolution:** Select Let's Encrypt explicitly:

```bash
docker exec acme-sh acme.sh --set-default-ca --server letsencrypt
docker exec acme-sh acme.sh --register-account -m admin@devlouix.com
```

Retry the issue command only after the account command succeeds.

### 8. Wrong container mount prevented Traefik from seeing certificates

**Symptom:** `/certs/erpsite.fullchain.crt` did not exist from Traefik's
perspective, even though host certificates were intended to be shared.

**Resolution:** Keep the host and container paths identical:

```yaml
- /etc/dokploy/traefik/certs:/etc/dokploy/traefik/certs:ro
```

Use those exact paths in the dynamic configuration:

```yaml
tls:
  certificates:
    - certFile: /etc/dokploy/traefik/certs/erpsite.fullchain.crt
      keyFile: /etc/dokploy/traefik/certs/erpsite.key
```

### 9. Wildcard Docker labels still attempted Spaceship issuance

**Symptom:** HTTPS worked only after manual certificate files were installed,
but Docker labels could still request another certificate through
`TRAEFIK_WILDCARD_CERTRESOLVER=spaceship`.

**Resolution:** Remove the wildcard ACME resolver from the Docker router.
Enable TLS manually and let the file-provider certificate supply it.

```yaml
- "traefik.http.routers.erpnext-sites.rule=Host(`${PROVISIONING_BASE_DOMAIN}`) || Host(`*.${PROVISIONING_BASE_DOMAIN}`)"
- "traefik.http.routers.erpnext-sites.entrypoints=websecure"
- "traefik.http.routers.erpnext-sites.tls=true"
- "traefik.http.routers.erpnext-sites.service=erpnext-sites"
```

Add explicit HTTP redirect routing:

```yaml
- "traefik.http.routers.erpnext-sites-http.rule=Host(`${PROVISIONING_BASE_DOMAIN}`) || Host(`*.${PROVISIONING_BASE_DOMAIN}`)"
- "traefik.http.routers.erpnext-sites-http.entrypoints=web"
- "traefik.http.routers.erpnext-sites-http.middlewares=erpnext-sites-https"
- "traefik.http.routers.erpnext-sites-http.service=erpnext-sites"
- "traefik.http.middlewares.erpnext-sites-https.redirectscheme.scheme=https"
```

## Verification checklist

### Certificate issuance

```bash
docker exec acme-sh acme.sh --list
docker exec acme-sh ls -la /acme.sh/erpsite.devlouix.com_ecc/

ls -lh /etc/dokploy/traefik/certs/

openssl x509 \
  -in /etc/dokploy/traefik/certs/erpsite.fullchain.crt \
  -noout -subject -issuer -dates -ext subjectAltName
```

The SAN output should contain both the apex and wildcard.

### Traefik mount

```bash
docker exec traefik-public \
  ls -la /etc/dokploy/traefik/certs
docker exec traefik-public \
  ls -la /etc/dokploy/traefik/dynamic
```

### HTTPS behavior

```bash
curl -vkI https://erpsite.devlouix.com/
curl -vkI https://sample.erpsite.devlouix.com/
curl -I http://sample.erpsite.devlouix.com/
```

The HTTP response should be redirected to HTTPS. The HTTPS response should
show a certificate whose subject alternative names include the requested apex
and wildcard names.

### Custom domains

```bash
docker logs --tail=100 erpnext-platform-worker-1
ls -lah /etc/dokploy/traefik/dynamic
docker logs --tail=200 traefik-public
```

For a custom domain that fails:

1. Verify public DNS.
2. Verify port 80 reaches Traefik.
3. Verify the custom route file is present.
4. Verify the generated resolver equals `letsencrypt`.
5. Check that Traefik and `frappe-frontend` share `dokploy-network`.

## Safe future changes

- Upgrade `traefik-public` or `lego` only after testing a staging Spaceship
  DNS-01 request.
- Do not remove `acme.sh` state or `/acme.sh` before confirming renewal.
- Back up `/etc/dokploy/acme.sh`, `/etc/dokploy/traefik/certs`, and the
  dynamic certificate YAML together.
- Treat the manual certificate as a temporary production workaround, not a
  reason to remove exact custom-domain HTTP-01 routing.
- When Spaceship LEGO support is verified, compare the issued SANs and
  expiry dates before migrating the wildcard router back to Traefik ACME.
- Keep custom route files isolated to the worker-generated filename pattern.
- Before changing wildcard provider settings, test HTTP redirect and HTTPS
  independently; wildcard routing can be working while certificate issuance
  is absent.
